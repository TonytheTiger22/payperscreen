Methodology

Exactly what each check does, signal by signal, including what we don't check yet, so you can decide for yourself whether it's enough for what you're using it for.

We'd rather you know the real boundaries of what's checked than have a result imply more confidence than the data supports. This page lists every signal behind every service, with nothing summarized away. If a signal isn't listed here, we don't check it, and we say so explicitly where a gap is a real limitation, not just an omission.

How to read "risk level" The email and IP checks don't use a list match. They run several independent signals and combine them. Each signal is marked critical or minor ahead of time, based on how strong a problem it would mean on its own. A single flagged critical signal sets redFlag: true and riskLevel: "high" by itself, regardless of how many minor signals also flagged. That's the whole purpose of the distinction. With no critical flags, risk scales with how many minor signals flagged: 0 is low, 1–2 is medium, 3+ is high. Every signal that couldn't be evaluated is marked unknown, never folded silently into a pass.

None of this involves an AI model. Every signal on this page, for every service, is plain deterministic code against a real data source. Given the same input and the same underlying data, it returns the same result every time.

Sanctions name screening

GET /screen, $0.02 per check

Fuzzy match against a list of names, not a composite of independent signals: one check, one data source.

What we check
List coverageSanctions lists loaded in our database: OFAC SDN, UN Security Council Consolidated List, EU Consolidated Financial Sanctions List, UK Sanctions List (FCDO). Only lists that are actually loaded are checked, every response names them in listsChecked, and /lists shows the live record count and last refresh date per list.
Match methodTrigram similarity against both primary names and known aliases, not an exact string match, so minor spelling differences, transliteration, and word-order changes can still surface a match.
What's returnedThe single highest-scoring candidate above an internal similarity threshold from each list, so a name that resembles entries on three lists returns up to three hits, one per list, strongest first. Not every candidate within a list.
What we do NOT check

Any list not shown in listsChecked or on /lists. "No match" means no match on the lists named in the response, nothing broader. Other national lists (Canada, Australia, Switzerland and others) are not included. We also don't screen for Politically Exposed Persons (PEP) status or adverse media (negative news). Both are separate, unbuilt products, not folded into this result.

Each list is a snapshot, not a live feed. Every list (OFAC SDN, UN, EU, UK and OFAC's crypto addresses) is re-downloaded automatically once a day; a failed download keeps the previous copy rather than leaving a list empty. If you need a same-day guarantee, cross-check anything high-stakes against the issuing authority's own list. /lists always shows the actual record count and last-refresh date, not a marketing claim.

Crypto wallet address screening

GET /screen-address, $0.02 per check

What we check
List coverageOFAC's sanctioned digital-currency address list only. 18 assets: XBT (Bitcoin), ETH, USDT, USDC, TRX, SOL, LTC, BCH, ARB, BSC, ETC, DASH, XMR, ZEC, XVG, BTG, BSV, XRP.
Match methodExact string match on the address, not fuzzy. EVM-family addresses (0x...) are compared case-insensitively; everything else (Bitcoin, Solana, etc.) is case-sensitive, matching how those address formats actually work.
Known hack proceedsA second, separate list: addresses publicly identified as attacker-controlled or holding stolen funds in major hacks. Sources are law-enforcement notices (the FBI's Bybit notice) and the victims' or security firms' own incident write-ups, each entry linked to where it was published. Reported as hackFunds, never as a sanctions hit. Today it covers Bybit, Kelp DAO, Drift, Truebit, Resolv and Step Finance; /lists shows the current count.
What we do NOT check

This source has no linked entity name, date of birth, or sanctions program per address, the upstream data simply doesn't carry that information. A hit tells you the address is listed and which asset; it can't tell you whose address it is or why it's listed. "Not sanctioned" means not on this one list. It is not a guarantee the address is otherwise clean, has no transaction history with sanctioned parties, or isn't a mixer/exchange hot wallet.

The hack list only flags the wallets named in its sources. Stolen funds usually move on through many more wallets, bridges and mixers within hours, and we don't follow them. It also only grows when a hack is publicly documented, so a recent incident may be missing.

Email trust check

GET /screen-email, $0.02 per check

A "fan-out and score" composite: 10 independent signals run in parallel, each judged pass/flag/unknown, then combined into one risk level. All of them are free and zero-key.

SignalSeverityWhat it actually checks
Syntax and mail servercriticalValid address format and the domain has an MX record at all. A domain that can't receive mail is flagged outright.
Disposable email providercriticalChecked against a maintained open-source list of known disposable/temp-mail domains (10minutemail, etc.).
Provider typeinformationalConsumer free-mail (Gmail, Yahoo, etc.) vs. a custom/corporate domain. Never flags either way on its own.
Domain registration ageminorHow long ago the domain was registered, via RDAP. Flagged if under 30 days old.
Domain certificate historyminorPublic log of every SSL certificate ever issued for the domain, via crt.sh, an independent age signal.
Mailbox verificationcriticalBest-effort. We connect to the domain's mail server and ask if the specific mailbox would accept mail (no message sent). Many mail servers block this or accept every address regardless (a "catch-all"), both cases come back unknown, never a false "verified."
Mail server reputation (DNSBL)criticalThe mail server's IP checked against the Spamhaus ZEN blocklist, the same blocklist the IP risk check uses.
Mail providerinformationalIdentifies well-known infrastructure (Google Workspace, Microsoft 365, Zoho, etc.) by fingerprinting the mail server hostname. Informational only.
Look-alike domain checkcriticalCompares the domain against major free-mail providers using edit distance. It catches deliberate look-alikes like "gmial.com" or "yah00.com."
Account typeinformationalFlags local parts like admin@, support@, noreply@ as a shared/role mailbox rather than an individual. Informational only.
A limitation worth knowing

The mailbox-verification probe runs on port 25, which some cloud hosting blocks outbound entirely. If it's blocked on our end, that signal comes back unknown on every single check, it's worth checking the detail field on that signal yourself rather than assuming it ran.

IP risk check (beta)

GET /screen-ip, $0.01 per check

IPv4 only. Two scored signals and one informational one. The smallest of the checks, and the most honest about it.

SignalSeverityWhat it actually checks
Blocklist status (Spamhaus ZEN)criticalDNS-based lookup against Spamhaus's ZEN blocklist. It flags known spam sources, botnet members, and hijacked netblocks.
Tor exit nodecriticalChecked against the Tor Project's own public exit-node list (refreshed hourly on our side). Flags that the address is a known point where Tor traffic exits to the open internet, origin of the underlying traffic is anonymized.
Network allocationinformationalWho the IP block is allocated to, via RDAP. Never scored: plenty of legitimate traffic comes from datacenter or cloud IPs, so this is context, not a verdict.
What we do NOT check yet

VPN/hosting classification and community abuse reports (AbuseIPDB) both need a paid key we haven't provisioned. IPv6 isn't supported at all yet, only IPv4. Private and reserved ranges (RFC 1918, loopback, etc.) are rejected outright with an error rather than a "low risk" result, since there's no public reputation to check for an address that isn't routable on the open internet.

Keeping this page honest

Every response from every endpoint already states exactly which signals were checked (signalsChecked, the signals array, or listsChecked). Nothing is checked silently, and nothing on this page should ever say more than the API itself returns. If we add a signal, remove one, or change what a severity means, this page gets updated the same day. See /docs for the full technical API reference (request/response shapes, pricing, payment mechanics) and /lists for live record counts on the list-based checks.

A data service, not a compliance service. What you do with a result (clear it, escalate it, hold a payment) is entirely your own process and your own regulatory responsibility.
